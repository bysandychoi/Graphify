# 가상 위치·층 연결 스키마 (T009)

> **이 문서는 개발·검증용 가상 스키마이며 회사의 실제 데이터 구조가 아니다.**
> 필드명, 키, 위치→층 산출 규칙은 전부 이 프로젝트에서 임의로 정한 것이다.
> 실제 연결 테이블·키·산출 방식은 problem.md 3절 "위치와 층"에 따라
> 미확인 상태다. 직렬화 형식(중첩 배열)도 개발 편의상 선택일 뿐 실제 입력
> 파일 형식을 가정하지 않는다.

## 배경

problem.md 3절: lot 현재 위치와 설비 층은 별도 데이터를 연결해야 파악할 수
있다는 전제로 진행한다. 한 lot의 후보 설비들이 서로 다른 층에 있을 수
있으며, 이 특성이 중요하다. 이 문서는 그 전제를 가상 스키마로 표현한다.

## 연결 방식과 참조 규칙

- `lot_id`는 `docs/virtual_schema/lot_data.md`의 `lot_id`를, `eqp_id`는
  설비 마스터(정의처 없음, `docs/virtual_schema/eqp_step_run_spec.md`
  "표현하지 않는 것" 참고)를 문자열 그대로 참조한다(필드명은
  `lot_data.md`에서는 `candidate_pairs[].eqp`, `eqp_step_run_spec.md`에서는
  `eligible_eqp_ids`의 원소다). **이 문서는** `docs/virtual_schema/resource_data.md`가
  정의한 참조 규칙(대소문자 구분, 앞뒤 공백 trim 없음, exact match)을
  `lot_id`/`eqp_id` 참조에도 그대로 채택한다 — `lot_data.md`/`eqp_step_run_spec.md`
  자신이 이 규칙을 선언한 것은 아니다.
- `lot_id`/`eqp_id`는 ID 변경 대상이다(problem.md 5절, T048/T049). 이
  값이 바뀌면 `lot_location`/`eqp_floor`의 해당 행도 함께 갱신해야
  한다. `location_id`도 바뀌는 대상인지는 **미확인** — problem.md 5절이
  "변경하는 모든 ID"라고만 하고 위치 코드가 ID에 해당하는지는 명시하지
  않는다. 이 문서는 그 여부를 확정하지 않는다.

## 누락과 오류를 구분하는 두 갈래

이 스키마가 만나는 문제는 problem.md 7절 기준으로 **정책이 이미 정해진
것**과 **아직 정하지 않은 것** 두 갈래로 나뉜다. 아래 두 표는 어느 문제가
어느 갈래인지 표시하며, 이후 각 테이블 설명은 이 분류를 그대로 따른다.

**이미 정해진 정책 (problem.md 7절 "위치·층 정보 누락", T053) — 누락
항목을 보여주고 확인을 요청하며, 확인·보완 전에는 표본 선택을 진행하지
않는다:**
- lot의 위치를 못 찾음 (아래 형태 1·2)
- 설비의 층을 못 찾음 (`eqp_floor`에 행이 없거나 `floor`가 null)
- 위치 코드는 있지만 그 코드의 층을 못 찾음(`location_floor_lookup`
  조회 실패, 아래 형태 3)
- 같은 lot에 서로 다른 위치가 중복 기재되어 현재 위치를 하나로 확정할
  수 없음 — "정보가 없는 것"은 아니지만 결과적으로 위치를 알 수 없다는
  점에서 같은 갈래로 다룬다.

**아직 정하지 않은 오류 정책 (problem.md 7절 "아직 정하지 않은 오류
정책", T054):**
- `location_floor_lookup` 안에 같은 `location_id`가 서로 다른 `floor`로
  중복 등장 — 위치를 못 찾는 게 아니라 **서로 다른 답이 두 개 있어서
  어느 쪽이 맞는지 판정해야 하는** 문제다.
- (설비 마스터가 생기면) `eqp_id` 자체가 존재하지 않는 설비를 가리키는
  경우 — 지금은 설비 마스터가 없어 "층을 못 찾음"과 구분할 수 없다(아래
  테이블 2 참고).

## 테이블 1: `lot_location` — lot의 현재 위치

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `lot_id` | string | `lot_data.lot_id`를 참조. |
| `location_id` | string \| null | 가상 위치 코드(불투명한 문자열, 그 자체에 층 의미를 담지 않는다 — 아래 테이블 3 참고). 값이 없으면(null) 위치는 알려졌지만 코드화되지 않은 경우를 뜻한다. |

한 `lot_id`는 최대 1행이라고 가정하지만, 서로 다른 `location_id`를 가진
중복 행이 있을 수 있다 — 이 경우 위 "누락과 오류를 구분하는 두 갈래"에
따라 **이미 정해진 정책**(현재 위치를 확정할 수 없음) 대상이다.

**"위치를 못 찾음"의 세 가지 형태 (모두 이미 정해진 정책 대상):**

1. **행 자체가 없음** — 어떤 lot이 `lot_data`에는 있는데 `lot_location`에
   행이 없다. "이 lot의 위치 데이터가 아예 없음"을 뜻한다.
2. **`location_id`가 null** — 행은 있지만 위치 코드가 비어 있다.
3. **`location_id`는 있지만 `location_floor_lookup`에 없음** — 코드는
   있는데 그 코드가 가리키는 층을 모른다(아래 테이블 3 참고).

이 문서는 세 형태를 구분해서 보여줄 수 있는 구조만 제공하고, T053이
구현할 정책 자체를 바꾸지 않는다.

## 테이블 2: `eqp_floor` — 설비의 층

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `eqp_id` | string | `eqp_step`/`lot_data`가 참조하는 설비 id. |
| `floor` | int \| null | 가상 층 번호. null이면 그 설비의 층 정보 누락. |

- `eqp_id`마다 정확히 1행이라고 가정한다. `lot_location`과 완전히
  분리된 테이블이다 — 하나로 합치지 않는다(같은 lot의 후보 설비가 서로
  다른 층에 있는 경우를 왜곡 없이 표현하기 위함).
- **행 자체가 없는 경우, 원인을 구분할 수 없다.** `eqp_step.eligible_eqp_ids`가
  참조하는 `eqp_id`에 대해 이 표에 행이 없을 때, 그게 "설비 자체가
  존재하지 않아서"인지 "설비는 있는데 층 정보를 못 모아서"인지는 설비
  마스터가 없어(`eqp_step_run_spec.md` "표현하지 않는 것" 참고) 이
  스키마만으로 구분할 수 없다. **이 문서는 그 구분이 불가능한 채로,
  일단 "층을 못 찾음"(이미 정해진 정책, T053 대상)으로 취급한다** —
  `lot_location`의 형태 1과 대칭이다. 설비 마스터가 나중에 정의되면,
  "설비 자체가 존재하지 않는 참조"는 별도의 아직 정하지 않은 오류(T054)로
  다시 분리해야 한다.
- `floor`가 null인 경우도 같은 정책(T053) 대상이다.

## 테이블 3: `location_floor_lookup` — 위치 코드 → 층 산출 (가상 규칙)

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `location_id` | string | `lot_location.location_id`와 매칭 |
| `floor` | int | 이 위치 코드가 속한 층 |

**가상 규칙(임의 정의, 회사 실제 산출 방식 아님):** `location_id`는 층
정보를 담지 않는 완전히 불투명한 문자열이다(예: `"LOC001"`, `"LOC002"`)
— 문자열 형식만 보고 층을 유추할 수 없게 일부러 이렇게 정했다. lot의
"현재 층"은 항상 이 표를 조회해서만 얻는다. 이렇게 하는 이유: 만약
`location_id`가 층 번호를 인코딩한다면(예: `"LOC-1-03"`), 인코딩된
값과 이 표의 `floor`가 서로 다를 때 어느 쪽이 맞는지 정하는 문제가
추가로 생긴다 — 이 스키마는 그 문제 자체를 만들지 않는 쪽을 택했다.
또한 이 프로젝트에서 건물(동) 단위 구분은 다루지 않는다 — 모든 층 번호는
하나의 공통 체계라고 가정하며, 서로 다른 건물의 같은 층 번호를 다른
것으로 봐야 하는지는 미확인이다.

`location_id`마다 정확히 1행이라고 가정한다. 같은 `location_id`가 서로
다른 `floor`로 중복 등장하는 경우는 위 "누락과 오류를 구분하는 두 갈래"에
따라 **아직 정하지 않은 오류**(T054)다. `lot_location`이 참조하는
`location_id`가 이 표에 없는 경우(조회 실패)는 **이미 정해진 정책**(T053,
위 형태 3)이다 — 이 둘은 서로 다른 문제이며 같은 정책으로 묶지 않는다.

## 예시 데이터

```json
{
  "lot_location": [
    { "lot_id": "LOT_V0001", "location_id": "LOC001" },
    { "lot_id": "LOT_V0002", "location_id": "LOC002" },
    { "lot_id": "LOT_V0003", "location_id": "LOC001" },
    { "lot_id": "LOT_V0003", "location_id": "LOC002" },
    { "lot_id": "LOT_V0004", "location_id": null },
    { "lot_id": "LOT_V0006", "location_id": "LOC999" }
  ],
  "eqp_floor": [
    { "eqp_id": "M01", "floor": 1 },
    { "eqp_id": "M02", "floor": 2 },
    { "eqp_id": "M03", "floor": 1 },
    { "eqp_id": "M04", "floor": null }
  ],
  "location_floor_lookup": [
    { "location_id": "LOC001", "floor": 1 },
    { "location_id": "LOC002", "floor": 2 }
  ]
}
```

problem.md 5절이 요구하는 위치·층 관련 비율은 두 가지 서로 다른 축이다
— 후보 설비의 층 분포(단일 층/여러 층)와, lot의 현재 층과 후보 층의 관계
(현재 층만/다른 층만/양쪽). 아래 예시는 둘 다 포함한다.

- `LOT_V0001`은 현재 `LOC001`(1층)이고, 후보 설비가 `M01`(1층)과
  `M02`(2층)라면 후보 설비는 **여러 층**에 있고, lot은 **현재 층과 다른
  층 모두에서** 처리 가능한 경우다.
- `LOT_V0002`는 현재 `LOC002`(2층)인데 후보가 `M01`(1층)뿐이면 후보
  설비는 **한 층에만** 있고, lot은 **다른 층에서만** 처리 가능한 경우다.
- (표에는 없지만) 현재 `LOC001`(1층)인 lot의 후보가 `M01`(1층)과
  `M03`(1층)뿐이라면, 후보 설비는 **한 층에만** 있고 lot은 **현재
  층에서만** 처리 가능한 경우가 된다 — 세 유형 중 나머지 하나다.
- `LOT_V0003`은 `lot_id`가 두 번, 서로 다른 `location_id`(`LOC001`,
  `LOC002`)로 나타난다 — 위 테이블 1에서 말한 "현재 위치를 하나로 확정할
  수 없는" 경우이며, 이미 정해진 정책(T053) 대상이다.
- `LOT_V0004`는 `location_id`가 `null`이라 형태 2(이미 정해진 정책,
  T053) — 층 비교 자체가 불가능하다.
- 표에 없는 `LOT_V0005`처럼 `lot_location`에 행 자체가 없는 lot(형태 1,
  T053)도 있을 수 있다.
- `LOT_V0006`은 `location_id`가 `LOC999`인데 `location_floor_lookup`에
  그 코드가 없다 — 형태 3(이미 정해진 정책, T053)이다.
- `M04`는 `eqp_floor.floor`가 `null`이라, 그 설비가 후보에 포함된 lot은
  테이블 2에서 설명한 "층을 못 찾음"(T053) 사례가 된다.

세 유형(현재 층만/다른 층만/양쪽) 비율과 두 유형(단일 층/여러 층) 비율을
계산할 때 위 누락·오류 사례(T053/T054 대상)를 분모에 포함할지, 제외할지,
별도로 표시할지는 이 문서가 정하지 않는다 — T029(층/위치 관계 분포 계산
로직)에서 분모와 중복 가능성을 명확히 표시해야 한다(problem.md 6절
"관계별 비율은 중복 가능성과 분모를 명확히 표시해야 한다").

## 이 문서가 표현하지 않는 것

- 실제 위치→층 산출 규칙(문자열 형식, 건물/구역 체계 등) — problem.md 3절
  기준 미확인.
- `lot_location`/`eqp_floor`/`location_floor_lookup`의 실제 연결 키와
  테이블 존재 여부 자체 — 회사 데이터에 이런 테이블이 실제로 있는지도
  미확인이다.
- 위치 이력(시간에 따른 위치 변화) — 이 스키마는 "현재" 위치/층 한
  시점만 표현하며, 관측 시각이나 이력 관리는 범위 밖이다.
- `location_id`가 ID 변경(T048/T049) 대상인지 여부 — 위 "연결 방식과
  참조 규칙" 참고, 확정하지 않았다.
- 축소 시 미참조 행 제외 여부 — 선택된 lot/설비와 연결되지 않는
  `lot_location`/`eqp_floor` 행은 제외될 수 있다(problem.md 5절, T047)는
  일반 원칙만 적용되며, 이 문서가 별도로 정하는 것은 없다. 빈 배열도
  세 테이블 모두에서 유효한 값이다.
